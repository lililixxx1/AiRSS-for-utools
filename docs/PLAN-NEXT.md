# PLAN-NEXT — 值得做的功能补齐路线（2026-09 盘点产出）

> 背景：2026-09-05 对照《RSS 阅读器功能详解》（`../rss-reader-features-top20-2026.md`，11 项对标功能）
> 做了全量代码盘点。结论：11 项中 6 项已落地且大多扎实（未读/星标、全文搜索、AI 摘要、
> 视图外观、快捷键、订阅管理主体）；真正的短板收敛为**两条主线**（全文提取、过滤规则）
> + **一组组织性小补齐** + **一项待定**（稍后读）。
>
> 本文档是路线与设计要点，不是实施方案：**每项启动前仍按惯例出独立实施方案、送
> plan-code-reviewer 审核通过后再动代码**；安全基线（PLAN-PHASE1 §7）与数据纪律（§4）不变。

| 优先级 | 项 | 价值 | 体量 | 依赖 |
|---|---|---|---|---|

并确认使用需求后再立项。

## 1. P0 — 全文提取（摘要型源抓原文）

### 现状基线

- 正文链路：feed 只存 `itemfull:{item._id}`（feed 自带 contentHtml 消毒产物，≤100KB），
  摘要型源只有一段 summary，阅读面板只能显示「（无正文摘要，请打开原文查看）」
  （`ReaderPanel.vue` 兜底分支）。
- 净化管线已齐：`article.js` 的 `sanitizeContent / htmlToText / makeSummary / extractCover`；
  抓取管线已齐：`http.js` `nodeFetch`（超时/解压/限流）。
- README 二期路线已挂名「全文提取（Readability）」，代码零落地。

### 需求定义

打开一篇**摘要型源**的文章时，自动抓取原文页面、提取正文、消毒后替换展示；
产物缓存，二次打开秒出；失败安静降级回摘要，不打断阅读。

### 设计要点

- **判定 summary-only**：正文纯文本长度低于阈值（建议首版 600 字符，`htmlToText` 现成）
  或与 `summaryText` 高度重合。阈值做成常量，实测定稿。
- **触发时机：懒抓**。打开文章时若命中判定且该源开启全文 → 预preload 抓取 + 提取。
  **不做刷新期 eager 抓取**（带宽与 90s 单轮预算爆炸，且为永不读的文章付费）。
- **每源开关**：`Feed.fullText`（boolean，默认 false）。摘要型源痛点个体差异大，
  自动对外发请求涉及流量/隐私预期，默认关、编辑订阅里开（`EditFeedModal` 加开关行）。
- **依赖选型（先 spike 再定）**：`@mozilla/readability` 需要 DOM；候选 `linkedom`（轻）
  vs `jsdom`（重、提取兼容性最稳）。**硬约束**：preload 锁 Node16/CJS、node_modules
  原样随包——两个候选都要先过「require 兼容 + 包体 + 真实源提取质量」三项 spike。
- **存储**：新前缀 `itemfullx:{item._id}`（提取版正文 + `at`/`src` 元信息）。
  **不写回 `itemfull`**：该 key 是 ingest 写序的一部分，覆盖会与刷新管线互相踩
  `_rev`；独立前缀让提取层与判重层（contentHash/T-09）完全解耦。
- **安全（不可破）**：提取产物必须过 `sanitizeContent` 同一管道再入库——双道信任
  模型下 preload 仍是唯一 HTML 生产方，Readability 输出按不可信输入处理。
- **联动点（实施时一并处理，勿漏）**：
  1. `searchContent` 目前只扫 `itemfull:` 前缀——需扩扫 `itemfullx:`（提取版更长，
     搜不到等于功能残缺）；
  2. `enrich`/`translateItem` 的正文输入在提取版存在时应优先用提取版（更完整的正文
     → 更好的摘要/翻译）；
  3. `retentionClean`/`deleteFeedCascade` 的级联删除要带上 `itemfullx:`；
  4. `ingest` 内容更新（contentHash 变化）时，旧提取版应失效（与 T-09 清 `ai` 同源纪律）。
- **失败降级**：站点反爬/超时/提取置信度低（Readability 返回 null 或过短）→
  显示原摘要 + 一次性 toast，`itemfullx` 不落库（下次打开可重试）。

### 数据模型影响

- `Feed` 增 `fullText?: boolean`（可选，旧文档 undefined 按关读；双侧同步
  `src/types/index.ts` ↔ `db.js`）；schemaVersion 维持 3（新字段全部可选）。
- 渲染层 `getItemFull` 路径需能取到提取版（preload 侧封装优先级：itemfullx > itemfull）。

### 验收要点（摘要）

- 摘要型源文章打开 → 全文出现（含图片懒加载/外链宿主打开等现有阅读行为不回退）；
- 二次打开零等待（缓存）；断网/反爬站安静降级；搜索能命中提取版正文；
- 保留清理/删除订阅后 `itemfullx` 无残留；`sanitize` 冒烟测试新增提取产物消毒用例。

## 2. P1a — 关键词过滤（静音词 / 高亮词）

### 现状基线

- 过滤器只有五种：`all/unread/starred/feed/category`（`data.ts` `ListFilter`）；
  无任何关键词/规则能力——这是对标榜第 4 名的完全空白。

### 需求定义

用户维护两组词：**静音词**（命中即从列表隐藏）与**高亮词**（命中标题时视觉强调）。
解决「订阅了高产源但只关心部分话题」的噪音问题，纯本地、零 AI 额度。

### 设计要点

- **存储**：`Settings` 增 `muteWords: string[]` / `highlightWords: string[]`
  （dbStorage，随 settings 序列化，**preload 零改动**）。
- **匹配**：标题（含 `titleDisplay` 口径，与搜索一致）+ 摘要，多词 OR（任一命中即生效，
  与搜索的 AND 语义不同——静音是排雷，宁多勿漏；文档里写明差异防误用）。
- **应用位置**：`data.filtered` getter 内、排序前。统计三卡（未读数）**不剔除**
  静音项——计数是事实，列表是视图，混在一起会让用户怀疑丢文章。
- **可透视（必须有）**：工具栏显示「已静音 N 篇」，可临时展开查看/一键暂停过滤
  （过滤类功能的信任底线：藏了什么必须看得见）。
- **高亮**：复用 `highlightSegments` 纯函数渲染，不加新机制。
- **入口**：设置页「过滤」组（词表编辑用简单 textarea 逐行解析，避免做复杂规则 UI）。

### 不做的（v1 边界）

正则规则、按源独立词表、自动动作（命中自动标已读/星标——有伤害性且不可预期）。
NewsBlur 式「点赞/点踩训练」不做：单机插件语料与反馈量撑不起来，关键词+标签已覆盖
主要诉求（见 §7）。

### 验收要点（摘要）

静音词命中即隐、计数不变、透视与暂停可用；高亮不破坏虚拟滚动性能；
settings 序列化旧数据升级无感。

## 3. P1b — 标签智能文件夹（盘活 `ai.tags`）

### 现状基线

- `Item.ai.tags[]` 已由 enrich/轻量批持续产出，但**只在摘要卡展示，无处消费**——
  相当于半成品原料闲置。

### 需求定义

v1 最小闭环：**标签可点**。摘要卡与列表上的 tag 点击 → `filter = {kind:'tag', value}`
过滤全库同标签文章；侧栏新增「标签」区展示聚合 top N（由 items 现算，无需持久化）。

v2（v1 用出需求再做）：持久化智能文件夹（dbStorage `airss:smartFolders`：
`{name, tags[], words[]}[]`），侧栏独立分组，本质是预置的复合过滤器。

### 设计要点

- `ListFilter` 增 `kind:'tag'`；`filtered` 匹配 `x.ai?.tags?.includes(value)`。
- **空态诚实**：AI 关闭的用户没有任何 tags，侧栏标签区不渲染（而非空白区），
  摘要卡无标签时不显示标签行——不制造「功能坏了」的错觉。
- 标签聚合在 `items` 上现算（getter），量级（≤ 每源 200 × 源数）无性能压力。

### 验收要点（摘要）

点标签过滤正确；AI 关闭时无空态残留；与搜索/静音词叠加行为符合直觉
（过滤器交集语义与现有 `filtered` 一致）。

## 4. P2 — 组织补齐三小件

三件独立、都小、互不依赖，可拆可并，适合任一轮插空做。

### 4.1 分类管理（重命名 / 合并 / 删除）

- 现状：分类是扁平字符串（`Feed.category`），由源隐式聚合（`data.categories`），
  想改分类只能逐个编辑源；无重命名/合并入口。
- 方案：侧栏分类项加 ⋯ 菜单（复用 `fi-menu` 模式）：**重命名**（bulk 更新该分类下
  所有 `feed.category`，走 `saveFeed` 逐个 put）、**合并到…**（DropdownSelect 选目标）、
  **删除分类**（成员归回「默认」）。纯渲染层 + 现有 db 接口，无 schema 变更。
- 嵌套文件夹**不做**（§7）。

### 4.2 手动排序（拖拽）

- 现状：源固定按 `createdAt` 排（`data.ts` `loadAll`）。
- 方案：`Feed.order?: number`；侧栏 HTML5 拖拽（Electron 环境可用；注意已知坑——
  拖拽引起的布局变化**禁止加 grid/高度过渡**，瞬时切换）；排序 `order` 优先、
  `createdAt` 兜底；OPML 导出按当前顺序。旧文档无 `order` 按 undefined 兜底，无迁移。

### 4.3 订阅 URL 可改

- 现状：`EditFeedModal` 无 URL 字段，源换域名只能删除重订（丢已读/星标/AI 产物）。
- 方案：编辑弹窗加 URL 字段（`feed.normalizeUrl` 校验）；保存时重置
  `etag/lastModified/lastError` 并立即 `refreshOne`。items 的 `feedKey` 不变，
  已读/星标/AI 产物全保留。
- **已知代价（明示接受）**：新旧 URL 若内容重叠，同一篇文章因 link/guid 不同会判重为
  两篇，出现重复——换域名场景通常旧源已停更，实际影响小。

## 5. P3 — 搜索规模化（spike 先行，索引为后手）

- 现状：`searchContent` 线性扫全部 `itemfull:`（+P0 后 `itemfullx:`），1.5s 预算截断，
  截断时 UI 已提示「已扫描前 M 篇」。「allDocs 万级真实耗时」是 README 未勾选的
  实机待验证项。
- **本项不是开发任务，是测量任务**：攒到约 1 万篇真实存量时实测
  `allDocs + 扫描`耗时，按结果走决策树：
  - ≤500ms：维持现状，关闭本项；
  - \>500ms：默认上「仅展示/扫描最近 2000 篇」降级（README 已备选项，UI 已有截断
    提示，改动极小）；倒排索引（写入期维护 token→ids 文档）仅在降级后仍不可接受时
    立项——它是持续写放大，不为假想的量级买单。

## 6. P4 — 稍后读收件箱（**待定**，依赖 P0）

- 价值判定前置：星标已覆盖「订阅内收藏」；稍后读的差异价值在「订阅外的任意网页」。
  uTools 场景有天然入口（复制 URL 呼出，与现有「订阅到 AiRSS」正则指令同构），
  但**是否真有此习惯只有使用者自己知道**——默认不排期，P0 落地且有真实需求信号再立项。
- 形态草案（立项时展开）：plugin.json 新 feature「存入 AiRSS 稍后读」（URL 正则）；
  伪源 `_id: 'feed:__later__'`（special 标记，刷新调度/通知/保留策略全部豁免）；
  item 由 URL 生成：title=页面标题、contentHtml=P0 提取+消毒产物、pubTs=存入时刻；
  已读/星标/搜索/AI 全链路复用现有 item 能力。

## 7. 明确不做清单（防止未来重复讨论）

| 项 | 不做的理由 |
|---|---|
| 高亮标注与笔记回流 | Readwise 模式一半价值在生态回流与多端同步；单机 uTools 插件做出来只剩本地划线，「深读沉淀」位已被 AI 摘要+段落翻译占据，投入产出差 |
| 长期归档 | 与现有保留策略刻意反向（每源 200 篇+星标豁免是设计选择不是缺陷）；utools 文档库膨胀会直接拖垮 allDocs/搜索；要归档调大 `keepPerFeed` 即可 |
| AI 信源推荐 | 额度分池（手动 120/日、后台 30/日）下 AI 调用应优先花在内容本身；推荐位易营销化 |
| RAG 对内容问答 | 单篇与摘要/翻译重叠，多篇受额度与线性扫描双约束 |
| 过滤训练流（点踩学习） | 单机反馈语料撑不起训练；关键词（P1a）+标签（P1b）覆盖主要诉求 |
| 嵌套文件夹 | 扁平分类+分类管理+智能文件夹已覆盖组织需求；嵌套是把 file manager 复杂度搬进阅读器 |
| 杂志视图 / 自定义主题色 | 设计语言刻意收敛（暖米白+单一橙色，design-system 全文围绕它）；发散选项与定位冲突 |
| 云同步 | README 二期挂名，但需同步后端与冲突合并矩阵，是独立大石块；本轮不纳入，需要时单独立项再议 |
| 卡片封面渐变生成 | 装饰性小项，不顺手牵进任何主线；想做什么时候单独半小时做掉 |

## 8. 执行纪律（沿用，逐项适用）

1. 每项启动前出独立实施方案送 plan-code-reviewer，通过才动代码（PLAN-ENHANCE 惯例）。
2. 改 `preload/index.js` 挂载后必跑 `node scripts/check-preload-mapping.js`。
3. 数据模型双侧同步：先 `db.js` 文档形态、再 `src/types/index.ts`；新字段一律可选、
   schemaVersion 不无故升版。
4. 安全基线不变：渲染层不注入原始 HTML（Readability 产物同样过 `sanitizeContent`）、
   密钥不出 preload、正文消毒唯一产源在 preload。
5. mock 层同形补齐（浏览器 dev 可验），三套 node 测试按项扩用例。
6. 已知坑清单（AGENTS.md）全量适用：原生 select 禁用（C17 组件）、渲染层对象过 IPC
   前 plainClone、URL 跨 realm 用字符串、grid 轨道禁过渡。
